# 00-03 / 00-04 — Backend Foundation and Authentication

## 00-03 Backend API Foundation

- `.env` values are loaded through typed settings with the `HCA_` prefix.
- SQLAlchemy uses the psycopg v3 driver, connection pooling and pre-ping.
- `/health/live` is a liveness check; `/health/ready` executes `SELECT 1`.
- Known, validation, routing and unexpected failures use the existing
  `error.code`, `error.message`, `error.request_id` contract.
- Supplied request IDs are accepted only when they are valid UUIDs.
- Configured mobile development origins use explicit CORS rules.

The existing `001_initial_schema.sql` migration remains unchanged.

## 00-04 Authentication & User System

- Public registration accepts an existing institution code and always creates
  an `instructor`; public callers cannot assign themselves the `admin` role.
- E-mail addresses are normalized before the database lookup and insert.
- Passwords are stored only as Argon2id hashes.
- Login errors do not reveal whether the institution, e-mail or password failed.
- Access and refresh JWTs have separate token types, expiry periods, audience,
  issuer, unique token IDs and tenant/user claims.
- `/api/v1/users/me` verifies the access token and reloads the active user from
  the database; a disabled user loses access immediately.

Refresh-token revocation and reuse detection require server-side session/token
state and are intentionally reserved for the next security-hardening migration.
