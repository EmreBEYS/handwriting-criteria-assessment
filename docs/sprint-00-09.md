# 00-09 — Scan Upload & Job Queue

## Scope

Sprint 00-09 introduces the asynchronous boundary for serial exam-paper
capture:

`Active exam → Private image upload → Queued scan job → Status polling`

OCR processing and human confirmation remain separate later stages. This sprint
stores the private source image and creates the durable database job consumed by
a future worker.

## API

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/api/v1/exams/{id}/scans` | Upload one paper and queue a scan job |
| `GET` | `/api/v1/exams/{id}/scans` | List scan jobs for an assigned exam |
| `GET` | `/api/v1/scans/{id}` | Poll one scan job's status |

The upload is multipart form data with `client_request_id` and `image` fields.
A new upload returns `202 Accepted`; retrying the same request ID for the same
user and exam returns the original job with `200 OK`.

## Validation, privacy and reliability

- Only assigned instructors can upload to an active exam.
- PNG, JPEG, HEIC and HEIF are accepted up to `HCA_MAX_UPLOAD_BYTES`.
- Images are stored in the configured private S3-compatible bucket with
  server-side AES-256 encryption.
- Object keys are generated by the server and never exposed in API responses.
- SHA-256 is recorded for traceability without logging image or student data.
- A request ID cannot be reused for another exam.
- If object storage fails, no scan job is committed.

Worker execution, OCR predictions and review/confirmation are outside this
sprint; queued jobs intentionally remain `queued` until that worker exists.
